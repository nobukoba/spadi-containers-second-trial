# RARiS run 20 ordering inspection (partial Issue #7 investigation)

This investigation includes actual files and one Apptainer replay capture; it is not a completed ARTEMIS tutorial. Fetch
`example_rawdata/raris_ac_lgad_202603/{00,01,02}/run000020.dat` from
`nobukoba/container-interfacing-nestdaq-eicrecon` at revision
`ccf94e725389b5d32b2cd167312deb88c6461eba`, then run:

```sh
python3 experiments/raris-ordering/inspect_raris.py \
  /path/to/00/run000020.dat /path/to/01/run000020.dat /path/to/02/run000020.dat
```

The parser uses little-endian FileSink v1 and 48-byte STF v1 headers, and the
AMANEQ v1 64-bit data words from `nestdaq-user-impl` revision
`47897e9bdc4dac2f429909b3fa8bf05ab93115d0`. A first heartbeat has top six bits
0x1c and a 24-bit counter; it is followed by a second word with top six bits
0x1e. The files contain STF records with 16-byte HBF headers and heartbeat
delimiters. The TF header is generated by TimeFrameBuilder. Offsets below are zero-based byte offsets of first heartbeat
words. All first words have adjacent second words.

Each starts with STF IDs `7818184, 7818188, 7818192, 7818196` and
heartbeat IDs `7818184, 7818185, 7818186, 7818187, 7818188, 7818189,
7818190, 7818191`. All adjacent heartbeat IDs advance by one in each entire
file: there are 11259, 11359 and 11259 unit steps respectively, with zero
non-unit steps. Thus no per-source HBF reordering is observed in these files;
source 01 continues for 100 HBFs beyond sources 00 and 02.

In the pinned source, STFBFilePlayer splits the payload at heartbeat pairs in
file order. TimeFrameBuilder buffers STFs by `timeFrameId` and
`MakeOutPartsFromSTFBuffers` appends their parts in each received STF's order;
it does not sort HBFs within the STF. For the first STF, the source code
therefore predicts that `7818184, 7818185, 7818186, 7818187` remains in that
order for each source. An Apptainer replay subsequently confirmed this sequence in actual output, as described below. Source arrival order within the merged TF is not guaranteed.

The ARTEMIS processor and commands are documented in the RARiS tutorials. The replay comparison above used the published FULL image with matching pinned components; the newly built image has not been tested.

The pinned TimeFrameBuilder applies `decimation-factor` to its **decimator**
channel, not to the ordinary `out` channel. The existing recipe configures
only `out` at port 5501, so assuming that this output contains one TF in every
1,000 would be incorrect. Confirm actual counts in a replay before using them
for the offline/online comparison.

The published `spadi-user-full.sif` was launched successfully with Apptainer
1.4.5 and contains ARTEMIS at the pinned revision, ROOT 6.32.06 and
TimeFrameBuilder. Its NestDAQ core revision is `eda728718362cc0ee169bea9b111ffc3fda7ca6b`,
which matches the current checkout. The image uses Redis and does not provide `valkey-server`.

The upstream ARTEMIS v1 streaming store uses a ZeroMQ SUB socket, while the
existing replay recipe provides a PUSH endpoint. A compatible input or adapter
must address this socket mismatch and FairMQ multipart framing before online
analysis can work. The HBF headers expected by the ARTEMIS store are present
in these input files.

A bounded Apptainer experiment used the published FULL image and source 01.
Passing the raw STF file directly to `art::v1::TStreamingEventStore` produced
repeated `No such decoder` errors; the run was stopped. Inspection of the
pinned source shows its TF probe consumes the STF header before the direct STF
fallback. As an experiment, `wrap_stf.py` preserved each STF byte-for-byte and
put a one-source TF header before it. With that wrapped file and `MaxFrames: 10`,
the store completed and the output tree contained 11 entries. The tree contained
only an event header, not detector histograms. This proves neither hit decoding
nor an offline/online comparison. The wrapper is an investigation tool; it is
not a substitute for the requested analysis.

## Replay capture

On the published FULL image (NestDAQ core `eda728718362cc0ee169bea9b111ffc3fda7ca6b`,
user implementation `47897e9bdc4dac2f429909b3fa8bf05ab93115d0`) the three
players and one TimeFrameBuilder ran with the recipe's 5501 `out` endpoint,
`decimation-factor=1000`, and `output-incomplete-tf=false`. A PULL receiver
captured 2,815 TFs and 8,445 source STFs. Every captured source STF's HBF ID
sequence matched the corresponding file, with zero mismatches. For TF
7818184 each source had `7818184, 7818185, 7818186, 7818187` both before
and after; TF 7818188 had `7818188, 7818189, 7818190, 7818191`. Source 01's
25 additional STFs timed out due to absent peers and were not emitted. This
is one run, not a guarantee about all ordering or other builds.

`capture.cc` is the receiver used in this experiment; its capture consists of
little-endian uint32 part length, uint32 ZMQ more flag, then part bytes.
`compare_capture.py` compares it with the three original files. The actual
capture is temporary and is not included in this repository.

A further bounded offline prototype used `RarisHist.C` as an ARTEMIS processor
following `art::v1::TStreamingEventStore`. For source 01, the first 11 HBFs
contained 80 hit words by direct byte inspection, and its channel, TDC and TOT
histograms each had 80 entries. The store's `MaxFrames: 10` produces 11 entries
in this version. The prototype uses uncalibrated raw units and has not yet been
validated across all sources or connected to online data; it is not an
installation-ready analysis.
